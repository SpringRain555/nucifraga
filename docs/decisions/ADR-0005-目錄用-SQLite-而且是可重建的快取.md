# ADR-0005：備份碟上的索引用 SQLite，而且它是可重建的快取，不是正本

**狀態**：已採用
**日期**：2026-10-23

## 背景

要讓「第二次備份」快，就得知道哪些檔案沒變。只看來源的大小與 mtime 就夠判斷，
但要跟**上一次的值**比，所以上一次的值必須存在某處。存的地方要：

- 跟著備份碟走（換一台電腦接上同一顆碟，照樣知道上一次的狀態）
- 數十萬筆也能快速查
- 壞掉的時候不會讓備份出錯

## 決定

- 每個備份碟放一個 `.nucifraga\catalog.sqlite`，用 `rusqlite`（bundled，見版本下限）
- `journal_mode=DELETE`，不用 WAL
- **它是快取，不是正本。** 正本是 `current\` 底下的檔案本身與 `_reports\` 的清單；
  索引壞了或版本不符就改名保留並重建（`ENG-001`），重建後第一次執行會比較慢，但結果正確
- 記的是**來源**的大小與 mtime，不是備份碟上的（exFAT 時間精度 10 ms，互比會一直誤判）

## 考慮過但沒選的

| 方案 | 為什麼不選 |
|---|---|
| 每次都比對備份碟上的檔案（不存索引） | 要對外接碟 `stat` 每一個檔案，USB 碟上慢；而且 exFAT 的 mtime 不可靠 |
| JSON／JSONL 索引 | 數十萬筆時每次都要整份讀進來；更新一筆要重寫整份 |
| 索引放在本機（`%LOCALAPPDATA%`） | 換電腦就失效；兩台電腦備份到同一顆碟會各自以為對方的檔案是新的 |

## 代價

- 備份碟上多一個二進位檔，使用者看不懂（但不需要看懂）
- SQLite 本身有 CVE 要追（2026 年 FTS5 那一件），所以不開 FTS5、版本下限在 versions.md

## 什麼情況要重新考慮

- 50 萬檔的基準測試中，第二次執行的「比對」階段超過 60 秒
